# ZED-X20P: evidence and validation gaps for base and rover support

Research for [#251](https://github.com/rodenj1/sp-rtk-base/issues/251), under [map #247](https://github.com/rodenj1/sp-rtk-base/issues/247). Audited baseline **8854c750f06ff321be29c9d29f9874484ce92b97**, version **0.10.0**. This is an acceptance-research plan, not a support declaration or implementation. Source links below are pinned to that baseline unless explicitly external.

## Conclusions and evidence status

- **Both roles are plausible, not bench-proven.** [u-blox's product page](https://www.u-blox.com/en/product/zed-x20p-module) lists RTK rover and base station with survey-in; [ArduSimple's board page](https://www.ardusimple.com/product/simplertk4-optimum-zed-x20p/) identifies simpleRTK4 Optimum as a ZED-X20P evaluation board usable as Base or Rover. Those are vendor assertions, not evidence that this application's configuration, decoding, ports or persistence work on the installed firmware.
- **Existing tests are useful F9P-oriented behavioral evidence, not X20P hardware evidence.** There is already an explicit synthetic X20P identity test. It proves `MOD=` passthrough, not firmware discovery or operational support. Profile validation independently rejects a model absent from its catalog. See [identity test L88–95][identity-test], [identity catalog L56–104][identity-catalog] and [profile validator L244–261][profile-validation]. The identity module's claim that dropping a YAML alone enables a new model is therefore too broad at this baseline.
- **“Connect” in the application is not necessarily read-only.** `DeviceService._after_connect` invokes saved-config repair; `UbloxDriver.repair_saved_config` can delete TMODE keys from BBR. Stage-one capture must bypass this path, not merely avoid clicking Apply. See [service L456–460][after-connect] and [driver L2857–2879][repair].
- **Receiver correction use is a separate acceptance gate.** NTRIP verification, relay frame counts, host writes and MON-COMMS reception cannot by themselves establish that a rover used corrections. Existing telemetry can tally RXM-RTCM `msgUsed`, but its presence and layout on the particular X20P firmware remain unobserved. See [driver L1596–1717][correction-driver].
- **Current bench access is blocked, not capability disproven.** Delegated task context reports USB `1546:01ab` on hermes-01, no bound tty interfaces, installed cdc-acm for kernel `6.8.0-138` while running `6.8.0-146`. This is supplied context, not independently re-observed here. It neither identifies the module/firmware nor proves receiver incompatibility. No hardware, ports, driver binding, host settings or receiver configuration were accessed or changed for this research.

### What was actually exercised

Source inspection and stdlib-only offline probes in this worktree:

1. Parsing `uv.lock` yielded **pyubx2 1.3.0**, **pyrtcm 1.1.12**, **sp-rtk-base-relay 4.1.0**. Dependency minimums are looser; validation must record the exact resolved environment, not only requirements ([pyproject L25–36][dependencies], [lock][lock]).
2. Imported `tools/probe_correction_delivery.py` without invoking `main`. `verdict({'corrections_written': 1})` returned **`[]`**: missing receiver telemetry does not make the helper red. A helper “GREEN” is insufficient for X20P acceptance. Its ratio tests are conditional and unknown verdicts are excluded ([probe L51–87][probe]).
3. Imported the synthetic TCP source fixture without starting a server. At 200 requested bytes, generated **8 complete CRC-valid frames, no tail**; at 201 bytes, **8 complete frames plus a one-byte partial tail**. Its random Type 1005 payload and final slicing are explicit ([source fixture L58–80][source-fixture]); this is a transport fixture, not realistic observations usable to solve RTK.
4. Enumerating tracked test assets found **no `.ubx`, `.rtcm`, `.bin`, `.pcap` or `.raw` files**. This does not exclude embedded byte fixtures: there are generated MSM frames and mocked messages. It establishes that no such file-based capture asset is currently tracked, not that every fixture is synthetic by extension alone.

The system Python lacks pytest, pyubx2, pydantic and pyrtcm. No dependencies were installed and no unit/integration/browser suites were run for this document. No parser replay or hardware acceptance result is claimed.

## Read-only-first staged acceptance research

**All experiments below are proposals requiring future explicit authorization.** “Read-only” means no receiver configuration/persistence/reset commands; UBX poll bytes may be transmitted. Passive capture is narrower. Hardware access itself is not authorized by this document. Host driver repair, power cycling, starting services, correction injection and published NTRIP output are separate approvals, not implicit consequences of approving a poll.

Before any stage, name the operator, exact board/port/firmware, permitted commands, maximum duration, whether the antenna/power may be touched, artifacts destination and stop/rollback condition. Never discover a tty by blindly probing ports. Stop on identity ambiguity, lost ownership or an unexpected configuration command.

## Concrete inventories and missing observations

### Configuration support/readback/save

Start with the actual key builders, not a generic u-blox list: [RTCM/protocol/scalar/TMODE key inventory L106–241][key-inventory]. Mandatory investigation groups:

- UART baud; measurement and navigation periods; dynamics; TMODE mode, survey limits and HP LLH/ECEF/fixed accuracy. Confirm units and supported value ranges on the installed firmware.
- Per-port input/output UBX/NMEA/RTCM3; all 12 existing RTCM matrix rows, including 4072.0/4072.1, across claimed ports. The read model also considers I2C/SPI ([RTCM read L1274–1304][rtcm-read]); the public matrix supports UART1/UART2/USB only. Establish whether the board's USB console represents receiver USB or a UART bridge before polling or offering USB-specific keys.
- Six legacy constellation enable keys, BeiDou B2, elevation mask, SPI enable; establish whether X20 signal changes require new key/control semantics. Full scalar reads currently index every expected key directly ([driver L1848–1879][scalar-read]); one missing key can break the whole assertion. Product “all-band” language is not evidence those F9-specific fields exist or mean the same thing.
- Per-port RXM-RTCM output key and MON-COMMS report layout needed for actual-use diagnostics. Unknown console setup presently touches multiple ports ([driver L1636–1663][correction-driver]); identify first or require deliberate approval for wider changes.
- RAM/BBR/Flash/default existence, omission/NAK semantics, layer precedence, VALDEL support and reboot behavior. `_read_stored_keys_locked` treats any NAK as empty ([driver L2892–2902][stored-nak]); an unsupported poll could therefore masquerade as “nothing saved.” Validate against independent controls and the firmware documentation.
- Legacy CFG-GNSS diagnostic, CFG-CFG save and CFG-RST variants are especially important compatibility investigations. `save_to_flash` sends CFG-CFG with devFlash and trusts ACK ([L1906–1926][save]); saved layer and lifecycle checks remain required. Do not generalize F9 HPG reset/dur workarounds to X20P ([survey L737–868][survey-driver]).

### Rover versus corrected survey

Existing corrected-survey support does provide application-owned correction delivery and position averaging; [ADR 0004][survey-adr] describes its separate, survey-scoped pull engine. The driver now separates TX serialization from the polling lock ([driver L293–300][tx-lock], [correction tests][correction-tests]); do not rely on the ADR's older single-lock timing wording as current implementation evidence.

Still owed: an explicit sustained rover product workflow, role-safe profile without mandatory base RTCM output, dynamics and base-mode selection, independent correction source lifecycle, navigation output/UI, startup/reconnect behavior, safe return from corrected-survey cancellation and saved rover behavior. Base acceptance and “corrected survey completed” must not silently satisfy that scope.

### Output/parsers/dependencies

[pyubx2 upstream](https://github.com/semuconsulting/pyubx2) has later X20 HPG updates, including [commit dabef9f4dbc7a8320b74e5a70a5a04eeb618acba](https://github.com/semuconsulting/pyubx2/commit/dabef9f4dbc7a8320b74e5a70a5a04eeb618acba). This is a reason to inspect differences and replay the **locked 1.3.0**, not proof an upgrade is necessary or sufficient. No matching receiver firmware was read here. Obtain firmware-specific primary interface documentation before approving keys, layouts or reset/save behavior; public product pages do not settle them.

Inspect relay 4.1.0's decoder, framing/resynchronization, subscriber drop accounting and signal lookup with actual new-band MSM cells. Compare direct receiver capture with forwarded byte stream/CRC/IDs/counts, including fragmentation, unknown IDs and mixed UBX/NMEA. Repeat F9P NAV scaling and HP coordinate tests when changing parser versions; [position parsing L2155–2231][position-parser] contains explicit pyubx2 pre-scaling assumptions. An opaque frame can be transported successfully while UI signal decoding fails: report these as separate capabilities.

## Capture package required from future authorized work

One manifest per physical board/firmware/role/transport, containing:

- Board SKU/revision, module marking/variant, full MON-VER, USB descriptors and tty/receiver-port mapping, host/kernel/driver, app SHA, dependency lock/version output, antenna/power/V_BCKP facts and environmental conditions.
- Raw timestamped directional UBX/RTCM/NMEA transcripts and request ledger, checksums/hashes, immutable original plus redacted derived copy, independent decoded expectations and documented unit/precision choices. Do not fabricate missing capture bytes or change checksums while anonymizing coordinates.
- `key-support` table: key ID/name/type/units, exact firmware doc section, layer, request, response/NAK/timeout/omission, value, optional/mandatory status and confidence. Include negative cases, not only successful responses.
- Base: survey/fixed/cancel transitions, readbacks and persisted layer diffs, station coordinates/ID, RTCM message/rate/epoch report and consuming-rover evidence. Rover: source provenance and epoch/signal coverage, written/received/used counts, CRC/overrun/drop failures, NAV status/correction age timeline and interruption/recovery control.
- Lifecycle/ownership logs and before/after states; exact test commands and results, excluded scope, remaining questions and recovery action. Strip NTRIP passwords/tokens and personal locations from public reports; keep hashes/provenance for restricted originals.

**Acceptance rule:** each feature is marked *documented*, *simulated*, *capture-replayed*, *bench-observed*, *failed* or *inconclusive*, with an artifact reference. “Supported” requires bench-observed behavior for the promised role and transport, passing independent software regressions, and verified restoration/persistence where claimed. None of those hardware statuses is earned by this document.

## Prioritized further investigations

1. Unblock host access only with explicit separate permission; capture identity before choosing firmware docs or declaring USB/UART support.
2. Establish firmware-specific key/layer/message support and a genuinely non-mutating capture path; neutralize connect-time repair in any future read-only application mode before using it on hardware.
3. Reconcile identity passthrough with catalog/schema validation; design role- and firmware-aware capabilities rather than broad u-blox constants or an `any` profile bypass.
4. Resolve base-centric profile/data-link invariants for an actual rover workflow, and define correction-use telemetry when RXM-RTCM is absent or changed. The current helper's missing-telemetry green result must not be acceptance evidence.
5. Acquire real captures, replay locked parsers/relay and investigate new bands/IDs; only then propose targeted dependency or implementation changes.
6. Authorize bounded RAM changes, then separately authorize base/rover corrections, persistence and lifecycle tests with an independent F9P control. Record failures/inconclusive cases, not just positive screenshots.
