# ZED-X20P UI/API impact audit (base and rover)

Research for [issue #250](https://github.com/rodenj1/sp-rtk-base/issues/250), under [map #247](https://github.com/rodenj1/sp-rtk-base/issues/247). Target: **ArduSimple simpleRTK4 Optimum / u-blox ZED-X20P**. Baseline: **`8854c750f06ff321be29c9d29f9874484ce92b97` (v0.10.0)**. All source links below are pinned to that baseline, not moving main.

## Scope and evidence boundary

This is source/API/model/test research, not an implementation or a receiver qualification. No receiver, Bluetooth, serial, relay, deployment, or host-configuration operations were performed. Tests were inspected, not executed against a receiver. The separate chip audit must supply the actual X20P firmware/protocol, keys, supported ports/signals, storage semantics and message layouts before conditional recommendations become implementation requirements. This document deliberately does **not** claim that F9P UBX support implies X20P support.

NiceGUI pages generally call `DeviceService` and stores directly; the REST API is a parallel adapter over those contracts, **not** an HTTP dependency of the pages. For example compare [GPS Apply callback](https://github.com/rodenj1/sp-rtk-base/blob/8854c750f06ff321be29c9d29f9874484ce92b97/src/sp_rtk_base/ui/pages/gps_config.py#L2538-L2608) with [REST Apply adapter](https://github.com/rodenj1/sp-rtk-base/blob/8854c750f06ff321be29c9d29f9874484ce92b97/src/sp_rtk_base/api/device.py#L433-L473). Tests must cover both entry points; changing an API handler alone does not protect the UI.

## Outcomes / highest-priority findings

1. **Model recognition is already extensible; profile acceptance is not.** `MOD=ZED-X20P` resolves as confirmed, but `Profile.hardware` validates against a closed catalog derived from `MODEL_FAMILY`, which lacks X20P. A YAML-only addition is therefore insufficient despite comments saying otherwise. Confirmed X20P has no family at this baseline. See [catalogs](https://github.com/rodenj1/sp-rtk-base/blob/8854c750f06ff321be29c9d29f9874484ce92b97/src/sp_rtk_base/models/hardware_identity.py#L56-L104), [resolution](https://github.com/rodenj1/sp-rtk-base/blob/8854c750f06ff321be29c9d29f9874484ce92b97/src/sp_rtk_base/models/hardware_identity.py#L124-L168), [profile validation](https://github.com/rodenj1/sp-rtk-base/blob/8854c750f06ff321be29c9d29f9874484ce92b97/src/sp_rtk_base/models/profile_models.py#L244-L261) and [existing X20P pass-through test](https://github.com/rodenj1/sp-rtk-base/blob/8854c750f06ff321be29c9d29f9874484ce92b97/tests/unit/test_hardware_identity.py#L88-L95).
2. **Capabilities are vendor-wide constants, not model/firmware qualification.** The u-blox driver advertises survey, fixed base, RTCM select, flash save, position, satellite and GNSS selection unconditionally. The legacy GNSS “capability probe” logs a result but does not change those flags. GPS config shows the entire connected form; survey hides its survey card based on `FIXED_BASE`, while its fixed card is merely connection-gated. See [driver flags](https://github.com/rodenj1/sp-rtk-base/blob/8854c750f06ff321be29c9d29f9874484ce92b97/src/sp_rtk_base/services/drivers/ublox.py#L398-L407), [diagnostic-only probe](https://github.com/rodenj1/sp-rtk-base/blob/8854c750f06ff321be29c9d29f9874484ce92b97/src/sp_rtk_base/services/device_service.py#L714-L735), [GPS visibility](https://github.com/rodenj1/sp-rtk-base/blob/8854c750f06ff321be29c9d29f9874484ce92b97/src/sp_rtk_base/ui/pages/gps_config.py#L1853-L1906) and [Survey visibility](https://github.com/rodenj1/sp-rtk-base/blob/8854c750f06ff321be29c9d29f9874484ce92b97/src/sp_rtk_base/ui/pages/survey.py#L671-L718).
3. **There is a compatibility bypass in the base-invariants remedy.** Survey's one-click remedy merges the hard-coded F9P built-in, minus baud, then calls whole-form Apply. It does not use profile compatibility to choose an X20P-safe remedy. Removing the F9P profile from the picker does not protect this path. See [base check/remedy](https://github.com/rodenj1/sp-rtk-base/blob/8854c750f06ff321be29c9d29f9874484ce92b97/src/sp_rtk_base/services/device_service.py#L911-L983).
4. **The configuration schema is base-biased even when TMODE is disabled.** Both profile and Apply require nonempty UART data-link ports, 1005 enabled on at least one of them, and some RTCM output on every chosen port. An ordinary input-only rover or USB-only base cannot express its intended configuration through this contract. This is more than relabeling “base” to “receiver.” See [port scope](https://github.com/rodenj1/sp-rtk-base/blob/8854c750f06ff321be29c9d29f9874484ce92b97/src/sp_rtk_base/models/profile_models.py#L65-L76), [profile rules](https://github.com/rodenj1/sp-rtk-base/blob/8854c750f06ff321be29c9d29f9874484ce92b97/src/sp_rtk_base/models/profile_models.py#L175-L242), [Apply rules](https://github.com/rodenj1/sp-rtk-base/blob/8854c750f06ff321be29c9d29f9874484ce92b97/src/sp_rtk_base/models/profile_models.py#L311-L347).
5. **Multi-band visibility and configuration are incomplete.** Writes select six constellations plus one BeiDou B2 boolean, not a full signal catalog. NAV-SIG and MSM adapters place L5/E5a/B2a and other unlisted bands in `other`; the verdict judges L1/L2 only. See [config fields](https://github.com/rodenj1/sp-rtk-base/blob/8854c750f06ff321be29c9d29f9874484ce92b97/src/sp_rtk_base/models/profile_models.py#L148-L157), [quality contract](https://github.com/rodenj1/sp-rtk-base/blob/8854c750f06ff321be29c9d29f9874484ce92b97/src/sp_rtk_base/models/signal_quality_models.py#L21-L64), [NAV-SIG mapping](https://github.com/rodenj1/sp-rtk-base/blob/8854c750f06ff321be29c9d29f9874484ce92b97/src/sp_rtk_base/services/drivers/ublox.py#L2033-L2057), [MSM mapping](https://github.com/rodenj1/sp-rtk-base/blob/8854c750f06ff321be29c9d29f9874484ce92b97/src/sp_rtk_base/services/signal_quality/msm.py#L28-L51).

## API and schema implications

- Keep `/api/device/status` identity and generic connection semantics compatible where possible. Extend capability detail rather than making a vendor badge synonymous with support. Existing `/capabilities` list can remain a coarse summary, but cannot convey allowed signals, rate limits, available matrix cells or persistence support.
- `ReceiverAssertion`, `ReceiverScalarConfig`, `ReceiverConfig`, `Profile`, diff paths, apply-step dispatch, UI renderers and API validation must evolve together. Simply adding widgets leaves required readback fields and safety guards wrong. A capability-aware snapshot should distinguish **known value**, **unsupported field**, and **read failed**; using optional defaults to conceal read failure is unsafe.
- Adding hardware token alone need not bump schema version. Introducing role, per-signal selections, numerical RTCM rates or nullable/conditional snapshot fields changes serialized meaning: define version/migration and preservation of v1 F9P files explicitly. Current accepted versions are only `{1}` ([version/catalog](https://github.com/rodenj1/sp-rtk-base/blob/8854c750f06ff321be29c9d29f9874484ce92b97/src/sp_rtk_base/models/profile_models.py#L55-L76)), and merging always asserts matrix and measurement period even where other profile fields are omitted ([merge semantics](https://github.com/rodenj1/sp-rtk-base/blob/8854c750f06ff321be29c9d29f9874484ce92b97/src/sp_rtk_base/models/profile_models.py#L660-L738)).
- Profile compatibility currently annotates listing/picker; Apply carries an assertion and ports, **not a profile/hardware identifier** ([envelope](https://github.com/rodenj1/sp-rtk-base/blob/8854c750f06ff321be29c9d29f9874484ce92b97/src/sp_rtk_base/models/profile_models.py#L311-L347)). Therefore capability/role validation must use the connected receiver before reads/writes, not trust a selected profile, user-supplied hardware string, or disabled dropdown option.
- Full read failures can prevent page load and post-write result construction. Unsupported keys must be excluded from qualified batches, but transport timeout or a supported key missing from a reply must remain an error. Do not convert all failures to empty matrices or zero-valued fields.
- `status=ok` currently follows final assertion diff, not an independent all-steps-succeeded condition ([result decision](https://github.com/rodenj1/sp-rtk-base/blob/8854c750f06ff321be29c9d29f9874484ce92b97/src/sp_rtk_base/services/device_service.py#L1472-L1524)). New hidden invariants such as NAV ratio or signal combinations need explicit result/verification treatment; otherwise a failed step with no represented mismatch can escape the synchronization verdict.

## Questions to reconcile with chip/board audit

1. Which exact MON-VER MOD/hwVersion/FWVER/PROTVER values identify this module and supported firmware? Is a family tag warranted, and which fallback evidence is deterministic? Do not equate product family naming with identical key compatibility.
2. Which simpleRTK4 Optimum USB/bridge/UART connectors expose UBX and RTCM? Which receiver port IDs/protocol slots does MON-COMMS report? Are any app-modeled USB/I2C/SPI ports absent or inaccessible? What are factory baud and approved detection rates?
3. Which CFG-VALGET/VALSET/VALDEL keys and storage layers are supported? Does CFG-CFG save work, is Flash present, what outranks it after reset, and is deletion of TMODE BBR keys valid? Should this model ever receive the old-residue repair hook?
4. Which constellations and individual signal IDs/enable keys are available, including NavIC if applicable, and what combinations are legal? What replaces or supplements the legacy CFG-GNSS query? Is BeiDou B2 boolean the same concept on this firmware?
5. What measurement/navigation ratios, time-reference requirements, dynamics values and rate limits apply by signal set/base vs rover? Can NAV=1 be enforced, and what must the assertion read to prove it?
6. Is native TMODE survey supported? Which TMODE coordinates/high-precision components, NAV-SVIN units/flags, transition delays and reset semantics apply? What high-precision solution is authoritative for corrected averaging, and how are epochs correlated?
7. Which RTCM messages can the receiver **generate** on each port, versus **accept/use** as rover input? Are current 4072 variants, MSM4/MSM7 and GLONASS bias rows applicable? Which extra MSM rows are needed to represent enabled signals? Can numeric output dividers be preserved?
8. Are NAV-PVT carrier/validity/differential/correction-age fields and NAV-HPPOSECEF scaling unchanged? Does RXM-RTCM still provide received/used/CRC verdicts, and are MON-COMMS counters equivalent? What does missing telemetry mean, without assuming no corrections?
9. Which NAV-SIG gnssId/sigId mappings and RTCM RINEX signal codes represent all bands? Do used/above-mask NAV signals match generated MSM signals? What quality definition is defensible for L1/L5-only or other supported combinations?
10. Product rather than chip decision: is rover scope “configure X20P for an external correction input,” “temporary corrected survey,” or a persistent app-managed moving rover? The last requires a lifecycle/UI/API contract not provided by renaming existing controls.

## Recommendation / release gate

Retain the u-blox registry, generic identity/status, network source verification, shared form/live diff mechanisms and correction-feed safeguards where qualified. First reconcile model/firmware capability descriptors and safe read/write catalogs, then fix hardware-token acceptance, role-aware profile/apply contracts and the F9P invariant-repair bypass. Only then add approved X20P base/rover recipes and multi-band/rate/status controls. **A displayed X20P model name or green source verification is not acceptance evidence for base or rover operation.**

This artifact resolves the research deliverable only. It does not change issue/map state, implement controls, or authorize a receiver operation.
